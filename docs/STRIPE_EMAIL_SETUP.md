## Free email

Use Brevo Free as the preferred candidate. Set `EMAIL_PROVIDER=brevo`, `BREVO_API_KEY`, `EMAIL_FROM` and `EMAIL_DAILY_LIMIT=300`; activate transactional sending and verify the sender. Use display name **KSigdillas Tickets**, with reply-to **zachzapalac@gmail.com**. An owned domain can supply a sender without a paid mailbox. Without one, verify Brevo's supported Gmail/sender-rewriting setup and inspect the actual delivered From address. No email account/domain was created by the implementation.

Brevo receives one email per order, all QR PNGs as attachments, and readable secure links for every guest. Its API attachment shape differs from Resend; the Brevo template provides an attachment explanation and ticket links rather than broken inline image references. The existing Resend adapter continues to render inline QR images. A 50-guest synthetic message is covered by local tests; actual inbox rendering still needs a small real delivery test.

Configure Brevo transactional delivery callbacks to POST `/api/email/webhook` with custom header `x-ksigdillas-webhook-secret` matching `EMAIL_WEBHOOK_SECRET` (32+ random characters). Set this using Brevo's webhook authentication/header configuration, not a secret URL parameter. Include request/delivered/deferred/hard-bounce/soft-bounce/blocked/invalid/spam/error events. The handler persists early callbacks, correlates provider message ID and recipient, deduplicates, and protects newer delivery status from older events. Confirm exact event configuration with the account before activation.

Free quotas are finite. The queue reserves at most 300 Brevo or 100 Resend attempts per rolling 24 hours; use a lower configured limit to reserve headroom for other account activity. Provider 429s remain queued. Ambiguous responses and interrupted sends are held for staff inspection to avoid blind duplicate delivery. In **History & recovery**, record the confirmed provider message ID or explicitly retry after checking logs. Accepted, delivered and bounced are distinct statuses.

## Scheduler and monitoring

- Run the authenticated job endpoint once per minute. It expires local quotes, reconciles Stripe sessions/events/refunds, sends bounded email batches, processes delivery callbacks, and reports attention required.
- A compatible external scheduler can POST with `Authorization: Bearer <secret>`. `npm run jobs:run` does one such invocation using securely supplied process variables. Vercel Cron can GET the same endpoint; provision `CRON_SECRET` equal to `MAINTENANCE_JOB_SECRET` and verify the hosting plan supports the cadence/function duration. No recurring service was provisioned and no paid upgrade was made.
- Independently monitor the same authenticated endpoint with `?health=true` for a missing healthy heartbeat (over five minutes), and monitor worker 503/nonzero-attention results. Choose an approved operator notification destination when connecting the monitor; the application has not sent any alerts externally.
- Test this with browsers closed: fail an email safely, restore the service, and observe queued recovery. Also stop the test scheduler to prove the heartbeat monitor works. Do not count a manually called endpoint as proof that a recurring scheduler exists.

## Brother tracking and existing sales

In the organizer desk open **Brother contributions**. Add the real roster and approved aliases. The public checkout uses the roster for the optional brother field; cash sales can record a seller too. Staff records personal donors on money and food entries independently of the benefiting sorority. No-team gifts are supported. The private report separates ticket units/base revenue, personal cash gifts, and retail packages/points; CSV export protects spreadsheet cells from formulas. It introduces no public brother ranking or duplicate event points.

Corrections require a reason and the current revision. Shared gifts can be allocated only up to their verified source amount. Archived/renamed brothers retain history. Original Stripe free-text referrals are preserved; ambiguous/unmatched answers are unassigned until organizer correction. Original multi-ticket orders with only a buyer name retain “Guest N (name pending)” for other attendees.

Before cutover run `npm run ops -- check-stripe-import`, review, then explicitly `import-stripe`. These verify either explicitly approved current/historical Payment Link and paid sessions, map only the approved catalog and custom field keys, and avoid overwriting existing seller corrections on re-import. Refunded/disputed or incomplete historical sessions are counted as needing review and are not admitted through an automatic fresh import. Reconcile those cases before retiring the old sales paths. No real historical orders were imported during development.
